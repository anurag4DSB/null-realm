Flow 2: Cross-Repo Linking link_repos

After indexing, link_repos() creates XREF edges connecting symbols across repositories using package.json dependency resolution.

graph LR subgraph CS["cloudserver"] A1["objectPut()"] -->|CALLS| A2["putObjectMD()"] A3["<module>"] -->|IMPORTS| A4["arsenal"] end subgraph AR["Arsenal"] B1["MetadataWrapper"] B2["MetadataWrapper.putObjectMD()"] B1 -->|CONTAINS| B2 end A2 -.->|"XREF (cross-repo)"| B2 A1 -.->|"XREF"| B1 style CS fill:#1e3a5f,stroke:#2e4a6f,color:#e0e0e0 style AR fill:#2e1a4f,stroke:#3e2a5f,color:#e0e0e0
1

Read dep_map from repos table

Each repo's package.json / go.mod dependencies are stored as JSONB during indexing. link_repos reads them from the database — no filesystem access needed.

2

Find importing files

For each dependency (e.g., cloudserver depends on Arsenal), find all files that have IMPORTS edges to that package name.

3

Match orphan CALLS to real symbols

Unresolved CALLS from importing files (e.g., putObjectMD) are matched against actual symbol definitions in the dependency repo (e.g., MetadataWrapper.putObjectMD in Arsenal). Case-insensitive repo name resolution handles GitHub naming differences.

4

Create XREF edges

Neo4j MERGE creates XREF edges tagged with the package name. These are separate from intra-repo RELATES edges — queryable, deletable, and don't interfere with per-repo operations.

code_search

Embeds your query with the same Vertex AI model, then finds the top-K nearest neighbors in pgvector. Searches across ALL repos simultaneously — JS, Go, Python, SQL, configs.

Semantic Cross-repo

graph_query

Starts from a symbol and traverses RELATES + XREF edges in Neo4j. Depth-limited BFS shows connected functions, classes, and cross-repo dependencies.

Structural XREF traversal

service_topology

Returns the full service graph: DEPENDS_ON, HTTP_CALLS, USES_CLIENT, USES_INFRA, EXPOSES. Derived from package.json + code patterns + Federation configs.
